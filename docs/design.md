# bitcoinl2 设计存档

状态：2026-09-28 讨论记录，作为实现依据。标"待确认"的部分还没定；待讨论事项见 §8，按顺序一次讨论一个。

## 1. 目标

假设比特币有 GSR（含 OP_CAT），在其上做一个 L2：

- **vault**：L2 在 L1 上的托管。它是一条 UTXO line，有唯一、不可伪造的 id。
- **存款**：用户把钱付给 program a，参数写在 OP_RETURN 里。program a 之间可以两两合并（数据哈希到一起），递归成更大的 program a。program a 和 vault 在同一笔交易里被花掉，就等于存入 L2，同时 vault 的 caboose 状态更新。
- **提款**：ZK 证明（目前是占位）授权 vault 释放一笔钱给 program b。program b 递归拆分，最后直接付给各收款人。

## 2. 环境

- **共识假设 GSR** = BIP 440（varops 预算）+ BIP 441（tapleaf 0xc2）。两者都是 Draft。
  - **opcode**：0xc2 leaf 恢复了 CAT、SUBSTR、LEFT、RIGHT、INVERT、AND、OR、XOR、2MUL、2DIV、MUL、DIV、MOD、UPSHIFT、DOWNSHIFT。
  - **数字语义**：无符号、小端、任意长度。SUB 下溢直接失败；1NEGATE、NEGATE、ABS 变成 OP_SUCCESS。
  - **限制**：单个栈元素 ≤ 4,000,000B，栈总量 ≤ 8,000,000B，元素个数 ≤ 32,768。
  - **预算**：交易 weight × 10,000。各项开销：哈希 50/字节，签名检查 500,000/次，复制 3/字节，比较 2/字节，算术 6/字节。BIP 440 的常数还会调整。
  - **没有内省 opcode**，内省仍然要用 CAT/Schnorr trick。0xc2 下 CHECKSIG 仍按 BIP342 执行，但 sighash 里的 tapleaf_hash 要按 leaf version 0xc2 计算。
  - **实现**：`jmoik/bitcoin` 的 `gsr` 分支；bitcoin-inquisition PR #119 尚未合并。
- **设计按 GSR 的共识限制来做（2026-09-28 已定）**：不按 0xc0 那条 80 字节的 relay 政策设计，测试 signet 必须允许 0xc2 使用大的 witness 元素。80 字节切块的办法（§7）只作为备选。
  - 单笔交易实际可用的空间：
    - 标准交易上限是 400k WU，大约相当于 400KB witness 或 100KB 非见证数据。
    - 直接交给矿工的非标准交易，最多可以到约 4M WU，也就是一整个块。
  - 单个元素 4MB、栈总量 8MB：一笔交易本身带不了这么多数据，只有在脚本里用 CAT 拼接时才可能接近，所以实际上不会成为约束。
  - 元素个数 32,768：在 400k WU 以内也不会成为约束。
  - varops 预算：400k WU 的交易约有 4×10⁹，按每字节 50 算，大约够哈希 80MB，足够用。BIP 440 的常数还会调整。
- **测试环境**：开了 GSR 的 signet，具体用哪条待确认。截至 2026-09-28 没查到公开的。
- **Relay 政策**：Bitcoin Core v30 起允许一笔交易带多个 OP_RETURN 输出，`-datacarriersize` 默认 100,000（按所有 OP_RETURN 的总和计算）。

## 3. 记号（spec 使用的字母）

- **P**：vault 的地址（scriptPubKey）。每一代 vault 输出都付到 P。脚本里不能写死 P，因为 P 是脚本自身的哈希。脚本在运行时从 sighash 读出"自己的地址"，这是 covenants-gadgets step 2 的做法。
- **T0**：创世交易。T1 是第一次迁移，Tn 是第 n 次迁移。
- 花一个 vault UTXO 时涉及三笔交易：
  - **X**：当前交易，vault 脚本在这里执行。
  - **T**：父交易，也就是创建了正在被花的这个 vault UTXO 的交易。
  - **Q**：祖父交易。T 的 in0 花掉的那个 UTXO 是 Q 创建的。
  - 举例：X = T3 时，T = T2，Q = T1。

## 4. vault：严格按 spec v0.1.0，有两处偏离（§4.3）

spec 副本在 `docs/spec/utxo-linearization-v0.1.0-en/`，来源见 §9。

### 4.1 身份（按 spec 原方法）

- **状态 envelope**：`"UTXOLIN" ‖ 01 ‖ phase ‖ [genesis_id 32B] ‖ app_root 32B`。GENESIS 状态 41B，不含 id；ACTIVE 状态 73B。
- **id = txid(T0)**，按 outpoint 的字节序，不是区块浏览器的显示序。T0 的状态是 GENESIS；T1 写入 id；之后每次迁移逐字节保持不变。
- **花 vault 时**（X 花 T 的 out0）：
  1. 认证 X 的全部字段（SIGHASH_ALL，Schnorr trick）。要求：in0 是 vault，且 prevout.vout = 0；out0 是新的 vault；最后一个输出是 caboose；其余输入输出都属于明确的辅助角色。
  2. 反射 T：重建 T 的字节，双 SHA256 后必须等于 X.in0 引用的 txid。然后读 T 的 caboose，得到旧状态 S。
  3. 反射 Q：重建 Q 的字节，双 SHA256 后必须等于 T.in0 引用的 txid。然后读 `Q.output[k]` 的地址。
  4. 按 Q 的这个输出选择分支：
     - 地址不是 P，走创世分支：S 必须是 GENESIS；新状态必须是 ACTIVE，且 id = txid(T)。
     - 地址是 P，走延续分支：k 必须为 0；新旧状态都必须是 ACTIVE，且 id 相同。
     - 其他情况一律拒绝。
- **为什么不可伪造**：任何人都能往 P 付钱，再附上一个抄来的 caboose。但这种 UTXO 的父交易，in0 花的是普通的钱，所以祖父检查会把它引到创世分支。创世分支要求旧状态是 GENESIS，抄来的 ACTIVE 状态会被拒。如果伪造者附的是 GENESIS，写入的就是它自己的 txid，等于开了一条新链，冒充不了别人。
- **讨论过、不采用的做法**：
  - 把创世 outpoint 写死在脚本里，让地址本身就是身份。安全上与 spec 等价，为了简单按 spec 走。
  - 第一次花费时不读 Q 的简化。

### 4.2 交易与内省（按 spec 原样）

- in0/out0 是 vault，caboose 是最后一个输出。其余输入输出都必须按 ROLE-1/2 划入某个辅助角色。
- nVersion = 2，nLockTime = 0，nSequence = 0xfffffffd。所有输入都必须是原生 segwit（scriptSig 为空）。
- 内省：SIGHASH_ALL（0x01，不带 ACP），ext_flag = 1，无 annex，codesep_pos = 0xffffffff，使用 G/G Schnorr trick（pubkey = R = G）。
- 金额：旧余额取 Spent(X,0).value，新余额取 X.output[0].value。每一项增减都必须有授权（VALUE-1..3）。

### 4.2.1 被反射交易的资源约束（P4a 实现时确定，2026-09-28）

- 父交易 T 和祖父交易 Q 通过规范解析读取，最多 8 个输入、8 个输出；scriptSig 必须为空；计数和输出脚本长度都用单字节 compact size 表示，也就是脚本短于 253 字节。
- 这同样约束创世交易的出资交易（创世分支里的 Q）：出资方可能需要先准备一笔满足条件的交易。GSR 下已经没有 520 字节的限制，所以 R1 只剩下这几条结构性约束。

### 4.3 与 spec 的偏离

1. **（已定）caboose 用裸 OP_RETURN 输出，不用 P2WSH 包装**：`scriptPubKey = 6a 24 ‖ H(state) ‖ LE32(r)`，共 38B，金额 0。
   - 理由：P2WSH 包装的 caboose 每次迁移都会留下一个无法修剪的 UTXO，因为节点看不到里面的 OP_RETURN，同时还要烧掉 330 sat。裸 OP_RETURN 则根本不进 UTXO 集。
   - 影响：spec 中 CAB-1/2 的 P2WSH 构造，以及 `vectors/` 里的 `witness_script_*` / `script_pubkey_*`，都要按这个改。
2. **（随 GSR 变化，具体值待定）** spec 的 R1 规定被反射的交易 ≤ 520B，这是 BIP347 下的限制。GSR 下它不再成立，新的上限由单笔交易 weight、标准性规则和 varops 预算决定。
3. **（P4b 实现，2026-09-28）锁定交易和超时交易的 nLockTime 不为 0**（§8.4）。因此脚本不再检查父交易 T 的 nLockTime；其他种类的交易仍要求 nLockTime = 0。
4. **（P4b 实现，2026-09-28）新状态由脚本自己构造，不再作为 hint 传入**：脚本从旧状态和当前交易算出 S′，再检查 caboose 承诺的正是 H(S′)。
   - 只有交易发起方可以自由选择的字段才作为 hint 传入：锁定时的保证金、L2 地址和退款哈希；完成时的新参数。
   - spec 的 E04（揭示的状态与 caboose 不一致）因此在构造上就不可能发生。

## 5. caboose 结构（2026-09-28 已定：acc 累加父交易 txid）

**存款数据怎么进入 acc**：数据不会被复制进 out0，out0 只是金额变多；数据是通过 txid 链接进 acc 的，并且比并入交易晚一步。

1. 存款交易 D：输出 a_L（金额 v），紧跟一个 OP_RETURN，只放 L2 收款地址（§6）。
2. 合并交易 M（可选，可递归）：花掉 a1、a2，产生新的 a，金额 v1+v2。M 的 txid 本身就承诺了它花掉的两个 outpoint。
3. 并入交易 Xn：in0 是 vault，in1.. 是 a；out0 是新 vault，余额恰好增加这些 a 的金额之和；最后一个输出是 caboose。这一步 a 只出现在 Xn 的输入 outpoint 里。vault 脚本不认 a 的地址，只检查金额；vault 的 id 由 a 自己的脚本检查（§6）。
4. 下一次迁移 Xn+1：`acc = H(acc ‖ txid(Xn))`，到这时 a 才进入 acc。

SNARK 的追溯路径：acc → Xn → Xn.in1 的 outpoint → M → M 的各个输入 outpoint → 各笔 D 的 OP_RETURN。用到的全部是链上的非见证数据。

**以下为最初提议的记录**：

用户方向：caboose 一方面承担身份识别；另一个字段基本上是用来"堆东西"的 hash accumulator，由最终的 zkSNARK 从链上信息重构并理解被哈希的内容。

提议沿用 spec 的 envelope，字节格式不变，只重新定义 `app_root` 的含义：

```
state   = "UTXOLIN" ‖ 01 ‖ phase ‖ [genesis_id] ‖ acc
caboose = OP_RETURN PUSHBYTES_36 <H(state) ‖ LE32(r)>
```

- **acc 的更新规则**：迁移 X（父交易为 T）时，`acc' = H(acc ‖ txid(T))`。
  - 脚本在反射 T 时已经算出了 txid(T)，所以几乎没有额外成本，也不需要解析存款或提款的内容。
- **acc 就是 vault 自身交易历史的哈希链**：SNARK 按 txid 从链上取回每一笔 vault 交易，重构出其中的存款（program a 输入）和提款（program b 输出）。
- **创世**：acc_0 由部署者设定，用来承诺 L2 的初始配置。到 T1 时，acc_1 = H(acc_0 ‖ txid(T0))。
- **提款证明**：公开输入用新的 acc'，它覆盖了到父交易为止的全部历史。X 本身的内容要等到下一次迁移时才进入 acc。
- **约束**：L2 需要的数据必须放在交易的非见证部分（比如 OP_RETURN），因为 txid 不承诺 witness。
- **备选方案**：acc 累加的是类型化事件，比如存款记 outpoint + 金额，提款记根 + 金额，而不是整笔交易的 txid。

## 6. program a（存款）（2026-09-28 已定）

- **身份写进脚本**：L2 id L 就是 vault 的 genesis id，即 txid(T0)。vault 一创建，L 就确定了。L 写进 program a 的脚本，每个 L2 有自己的存款地址 a_L。
  - program a 不携带任何数据，也不反射任何交易，只检查当前交易。
  - a 之间的互相识别，就是它们的地址相同。
  - a_L 的脚本里还写死了 P，也就是 vault 的通用地址。vault 本身不引用 a，所以不会形成循环。
- **存款交易 D**：输出 a_L（金额 v），再加一个 OP_RETURN，里面只放 L2 收款地址。
  - 这个 OP_RETURN 只给 SNARK 看，链上没有任何脚本读它，所以严格说它不是 caboose。它放在非见证部分，由 txid(D) 承诺，SNARK 沿 outpoint 链找到后读取。
  - 金额直接取 a_L 输出的实际金额，不用写进数据；L2 id 由 a_L 的地址隐含。
  - 格式已定（2026-09-29），见下面"存款格式与分类"。
  - 输出在创建时不经过任何验证。缺失或格式错误的存款由 SNARK 判为无归属，钱会留在 vault 里，用户拿不回来，所以钱包必须构造正确。
  - 如果以后给叶子 a 加退款，这里还要加一个退款地址。
- **合并交易 M**：M 中每个 a_L 输入都检查以下条件。
  1. 只有 out0 的地址等于自己的地址（self spk），也就是只产生一个新的 a_L。
  2. out0 的金额等于所有 a_L 输入金额之和。手续费由额外的付费输入承担，由谁付见 §8。
  3. 不需要给 a 用的 OP_RETURN，SNARK 沿 outpoint 追溯整棵树。可以带一个写聚合者 L2 地址的 OP_RETURN，a 不检查它。
  4. a_L 输入的个数有上限（实现取 2～4）。
  5. in0 不是 vault（P）。如果 in0 是 vault，这笔交易就是并入，按下面并入的规则检查。
- **并入交易 X**：in0 是 vault。每个 a_L 输入都只看当前交易，检查以下条件。
  1. in0 花费的地址等于 P（从 `sha_scriptpubkeys` 读）。
  2. 见证提供 X 的新状态 S′。H(S′) 必须与 X 的最后一个输出（caboose）一致，且 S′.id == L。
  3. out0 − in0 == 本交易中所有 a_L 输入的金额之和。最初写的是 ≥，实现时改成相等：模板里 a 的位置上只能是 a_L，vault 自己的 leaf 也要求恰好相等。
  - 为什么这些就够了：X 要有效，in0 上 vault 自己的脚本必须通过，而它已经保证 S′ 是真 vault 的合法后继。伪造的 P 输出花不出去，克隆出来的 vault id 又不同。
- **实现（2026-09-28，`vault/src/program_a.rs`）**：每个 leaf 对应一种固定的交易模板。输入下标作为 hint 传入，由签名检查认证，所以同一个 leaf 可以在任意输入位置执行。
  - 合并，j = 2～4：输入 `[a×j, fee]`，输出 `[a(Σ), change, 聚合者输出]`。
  - 并入，j = 1～4：输入 `[vault, a×j, fee]`，输出 `[vault, change, 聚合者 OP_RETURN, caboose]`。这和 vault 并入 leaf 的模板相同，vault 的树因此从 1 个 leaf 变成 5 个（迁移，加上并入 j = 1～4）。
  - 每个 a_L 输入的检查：
    - 模板里 a 的位置全部是 a_L，最后一个输入（fee）不是 a_L；
    - 除了合并交易的 out0，任何输出都不是 a_L。vault 的 leaf 允许任意 segwit change，所以"并入时 change 付给 a_L"只能由 a 来拦；
    - 合并：out0 是 a_L，金额 == Σa；out1（找零）和付费输入都必须是原生 segwit（2026-09-29 加，见"存款格式与分类"）；
    - 并入：in0 的 spk == P，out0 − in0 == Σa；S′ 长 73 字节，H(S′) 等于 caboose 里的哈希，S′ 的头部等于 `MAGIC ‖ 01 ‖ ACTIVE ‖ L`。
  - Schnorr trick 的调整方式：合并交易改聚合者 OP_RETURN 末尾的 4 字节 nonce，并入交易改 caboose 的 r。因此聚合者 OP_RETURN 的格式是 `聚合者 L2 地址 ‖ nonce`，SNARK 解析时要允许末尾这 4 个字节。a 不检查这个输出。
  - 存款的构造器：`deposit_tx`，按下面的存款格式构造。
  - 大小（模拟器实测）：

    | | leaf | 整笔交易 |
    |---|---|---|
    | 合并 j = 2 / 3 / 4 | 615 / 678 / 741 B | 865 / 1,315 / 1,841 vB（加了 out1 和付费输入的检查之后） |
    | 并入 j = 1 / 2 / 3 / 4 | 724 / 787 / 850 / 914 B | 1,552 / 2,097 / 2,718 / 3,375 vB（P4b 之后） |

    每多一个 a 输入，合并交易多 440～510 vB，并入交易多 540～660 vB。原因是每个 a 输入都要带一整套 SIGHASH_ALL 数据作为 hint，这套数据随输入个数增长；再加上 leaf 脚本和 control block。所以交易大小随 j 超线性增长。
- **存款格式与分类（已定，2026-09-29）**：
  - 目的有两个：限制证明者的工作量；让追溯的人（电路）只凭 txid 覆盖的数据就能区分存款和合并。witness 不被 txid 覆盖，所以标记只能放在 OP_RETURN 里。
  - **存款格式**（L2 规则，只给符合格式的存款入账）：
    - 最多 8 个输入，scriptSig 全为空（也就是原生 segwit 输入）；
    - 输出恰好是 `[a_L(存款额), OP_RETURN <"L2D\x01" ‖ 32 字节收款地址>, 可选的原生 segwit 找零]`，每笔交易只存一笔；
    - 这样非见证部分最多约 470 字节，每笔存款最多 8 块 SHA256。
    - 不符合格式的存款不入账，钱留在 vault 里。钱包必须按格式构造。
  - **合并 leaf 加两条检查**：out1（找零）必须是原生 segwit；付费输入必须是原生 segwit。
    - 第一条保证合并交易的 out1 永远不会带存款标记。否则聚合者可以把合并出来的总额伪装成一笔存款，记到自己名下。
    - 第二条保证合并交易的 scriptSig 全为空，大小有上限。
    - 代价：每个合并 leaf 多 61 字节。
  - **分类规则**（`ProgramA::classify`）：从一笔并入交易出发往下追，遇到创建某个 a_L 输出（第 vout 个输出）的交易 M：
    - M 的 out1 带存款标记：它就是存款，而且一定是真的，因为真正的合并带不上这个标记。只有 vout = 0 并且 M 符合存款格式时才入账。
    - 否则 M 必须符合合并模板：vout = 0，2～4 个 a 输入加 1 个付费输入，3 个输出，out0 是 a_L，out1 是原生 segwit。符合的话，接着去追它的 a 输入，每个输入都必须花的是 a_L 输出。program a 保证真正的合并满足这一点。
    - 都不是：无归属。
  - 剩下的一种捣乱：有人自己出钱造一笔"长得像合并"的交易，逼证明者去哈希它背后的大交易。攻击者要赔掉这笔钱和大交易的手续费，证明者只是多算一些哈希，可以接受。
  - L1 上不会重复入账：一笔 a_L 输出被并入之后就被花掉了。证明这边只要保证相邻两次证明处理的历史首尾相接（§7 第 6 条），每笔存款就恰好入账一次。
- **vault 不识别 a 的地址**：在脚本里算 taproot 地址需要 EC 运算，GSR 里没有。所以 vault 只把额外输入当作一般的资金流入，归属由 SNARK 判定。
- **不需要谱系回溯**：SNARK 看到的是真实的交易图和真实金额。
  - 伪造的 a_L 只能装着伪造者自己的钱，它那棵子树会被 SNARK 隔离。
  - 合法的 a_L 只能被满足上述条件的交易花掉。
- **退款（2026-09-28 已定：不做）**：
  - 合并和并入都是 permissionless：任何人，包括存款人自己，只要付手续费，就能把 a 并进 vault。
  - 进入 acc 之后 L2 无法跳过：下一个提款证明必须处理 acc 里的每一笔存款，这就是强制包含。
  - vault 停摆等失败情形，交给 vault 的逃生通道处理（§8）。
- **聚合者激励（用户方向，2026-09-28）**：聚合者在 L1 上拿不到任何奖励；奖励由 L2 根据合并的实际情况发放。
  - 存款人不用填任何费用字段，存款 OP_RETURN 里只放 L2 收款地址。这样就没有"每笔存款的预算"，也就不存在被前面的人吃光的问题。
  - SNARK 能看到完整的合并树：谁合并了什么、每笔交易付了多少 L1 手续费（输入总额减输出总额）。
  - 已定（2026-09-28）：
    - 聚合者自己垫付 L1 手续费去合并、去并入。
    - 并入之后，L2 从存款的入账里扣取"合适的手续费"，分给聚合者。
    - 每笔合并交易和并入交易都带一个 OP_RETURN，写明聚合者的 L2 地址。a 的脚本不限制这个输出，只由 SNARK 读取。
    - 树里每一次合并都按自己那笔交易得到报酬，所以后来的人把别人合并好的 a 再往上合并时，抢不走前面的人的报酬。
  - 待定：怎样算"合适"。用户要求根据 L1 的实际行情来定，而规则必须能由 SNARK 从链上数据算出来。
    - 主要风险：聚合者故意多付 L1 手续费（比如和矿工合谋），好从存款里多扣钱，所以需要设上限。
    - 报销规则的形式：每笔存款每一步的报销上限 = 参考费率 × 该步写死的字节额度；实际报销 = min(实际手续费的分摊, 上限)。
    - 参考费率的来源有两个候选：
      - A. 最近区块的费率水平：SNARK 验证最近 N 个区块头（PoW）以及每块的 coinbase，用 coinbase 手续费总额估出每块的平均费率，再取中位数。
        - 优点：单个矿工或单个聚合者操纵不了。
        - 缺点：电路里要多做一个 L1 轻客户端（区块头 + coinbase 的 Merkle 证明），而目前的设计并不需要它。
      - B. 存款交易 D 自己付的费率：D 的手续费（输入减输出）SNARK 能算出来。
        - 优点：费用是存款人自己付的，聚合者操纵不了；不需要轻客户端。
        - 缺点：只反映存款那一刻的行情，之后费率上涨就没人愿意合并，只能等，或者存款人自己并。另外 D 的 witness 看不到，费率只能按非见证字节保守估算。
      - 已定（2026-09-28）：选 A。用户的判断是，这实际上把问题交给了 zk，可以克服。
    - A 的已知难点：SNARK 无法直接判断一串区块头是在主链上还是在分叉上。克服思路（草案）：
      1. genesis 配置（acc_0）承诺一个检查点区块头。SNARK 从检查点开始验证区块头链，包括难度调整规则，这样每个头都必须带真实的 PoW。
      2. 锚定：区块头链里必须包含那些打包了本 L2 合并交易和并入交易的区块（给出 Merkle 包含证明）。参考费率取这些区块之前 N 个块的中位数。
      3. 经济上的保证：要伪造中位数，攻击者得在私有分叉上以真实难度挖出大约 N/2 个以上的块，而每笔存款的报销都有上限，伪造的收益远小于成本。所以不需要证明"这是主链"，只需要保证"伪造很贵"。
      4. 把区块头的进度记在链上（用户指出：L2 交易越频繁，就越难分叉）。每个被 vault 接受的证明，都把自己验证到的 L1 链尖区块头哈希写进同一笔 vault 交易的 OP_RETURN，vault 脚本负责检查它与证明的公开输出一致。这个 OP_RETURN 由 txid 承诺，SNARK 沿 acc 可以看到它。下一个证明的区块头链必须从这个记录下来的链尖接着往后延伸。
         - 效果：分叉只能从最近一次记录之后开始。L2 活跃时两次记录之间只隔几个块，要在这么短的窗口里挖出 N/2 个以上的伪造块，实际上需要多数算力。
      5. 参考费率设硬上限（协议常数，具体值待定，用户明确不会高到 100 sat/vB 这种量级）。即使参考费率被操纵，每笔报销也不会超过"上限费率 × 字节额度"。
  - 聚合者承担的风险：如果 L2 停摆，垫付的钱拿不回来。
  - 之前讨论过、已被取代的方案：
    - 存款人设 max_fee 总上限。前面的人可能把预算吃光。
    - 存款人设 max_feerate，每步字节额度写死。
    - 固定 tip。
    - 合并时直接从 a 里扣手续费。

## 7. 提款与 program b（P4b/P5b 已实现，验证器仍是占位）

用户的想法：SNARK 决定一批提款交易，这批交易没法在一笔 L1 交易里全部放下，所以需要一种展开的办法。

1. **vault 提款交易 X**（带 SNARK 证明，目前是占位）
   - 输入输出：in0 = vault；out0 = vault，余额减少 W；out1 = b，金额为 W；out2 = OP_RETURN(R)；最后一个输出是 vault 的 caboose。
   - R 是一棵 Merkle-sum 树的根：
     - 叶子 = (收款 spk, 金额)。
     - 内部节点 = H(各子节点的哈希 ‖ 各子节点的金额 ‖ 本节点展开时可用的手续费额度)。
   - 证明的公开输入包括 acc′、R、W，以及 L1 链尖（见 §6）。vault 脚本检查 out1、out2 与这些公开输入一致。
   - **实现（P4b，2026-09-28）**：完成交易的输出是 `[vault, change, b(W), OP_RETURN(R ‖ H(清单)), 退款(保证金), caboose]`，change 统一放在 out1；b 的地址写死在 P 里。见 §8.4"实现"。
2. **b 的拆分交易**：任何人都可以发起。
   - 输入：花一个 b（金额 V）。它的根从父交易里紧跟在 b 后面的那个 OP_RETURN 读出，见证里给出这个根的各个子节点。
   - 输出：
     - 每个内部子节点，产生一个新的 b（金额为子节点金额），后面紧跟一个 OP_RETURN（子节点的根）。
     - 每个叶子，直接付给对应的收款 spk。
   - 脚本检查：
     - 子节点能哈希回这个根。
     - 每个输出的金额和地址与对应的子节点一致。
     - 手续费（V 减去输出总额）不超过根里写明的额度。
   - 扇出：GSR 下单笔标准交易（400k WU）可以放上千个输出，所以扇出可以取 64–256，两层就能覆盖几千到几万笔提款。
   - **实现（P5b，2026-09-28，`vault/src/program_b.rs`）**：比上面的提议更简单，脚本不再逐个检查输出。
     - **节点的承诺 R 就是拆分这个节点的那笔交易的 sha_outputs**，也就是它全部输出序列化后的 SHA256。
       - b 的脚本把 R 直接填进 SIGHASH_ALL 消息里 sha_outputs 的位置，再用 Schnorr trick 验证。这样每个输出的金额和地址都被钉死了，手续费也被钉死：它等于 V 减去输出总额，由树决定。
       - 脚本里不需要构造任何输出，也不需要知道子节点的内容。
       - 这仍然是一棵 Merkle-sum 树：内部节点的输出是各个子节点的 (金额, b) 和 OP_RETURN(子节点的 R)，它们的哈希就是这个节点的 R。
     - 拆分交易只有一个输入，就是被花的 b；nLockTime 可以随意取，用作 Schnorr trick 调整时的 nonce。
     - **规范布局**：
       - 内部节点的拆分交易输出为 `[b_1, D_1, b_2, D_2, …]`，其中 `D_i = OP_RETURN PUSHBYTES_32 <R_i>`，每个都是 43 字节；
       - 叶子节点的拆分交易输出就是各笔收款。
       - 扇出 ≤ 126，这样输出个数 < 253，计数只占一个字节。
     - **两个 leaf**：
       - root：花完成交易里的 b（vout 2）。先用通用解析器（8/8）解析父交易，再从下一个输出 `OP_RETURN PUSHBYTES_64 <R ‖ H(清单)>` 里取出 R。脚本约 1.1 KB。
       - internal：花拆分交易产生的 b。父交易按固定偏移切成 `head(47) ‖ 前面的输出(43·vout) ‖ 被花的 b(43) ‖ D(43) ‖ 其余` 五段，检查 head 里只有一个输入、被花的 b 恰好在这个偏移上，然后拼回去核对 txid，不需要解析。脚本 421 B。
       - 布局的正确性由 SNARK（证明）保证。布局不对的树，b 会花不出去，但钱不会被别人拿走。
     - 手续费目前是每笔拆分交易一个固定值（构造器的参数），还没有 P2A anchor。以后改成由 SNARK 按参考费率乘以这笔交易的大小来定。
     - DA：清单就是各笔收款输出序列化后首尾相接。有了它，再加上扇出和手续费这两个参数，任何人都能重建整棵树和每一笔拆分交易。测试里从完成交易的 witness 中找回清单、重建树，得到的根与完成交易承诺的 R 一致。
     - 大小（实测）：256 笔提款、扇出 16，共 17 笔拆分交易，合计 18,946 vB，平均每笔提款 74 vB，其中 31 vB 是收款输出本身。根拆分交易 1,842 vB，叶子拆分交易 1,069 vB。
     - relay 政策：内部节点的拆分交易有多个 OP_RETURN 输出。这在 Core v30 之后是标准交易；GSR 的 relay 政策本身还没定。
3. **b 不需要身份检查**。伪造的 b 只能花它自己的钱；b 只会拆分、不会合并，所以不会和合法的 b 混在一起。b 只需要反射父交易来读根。
4. **手续费**：每个节点展开时的手续费由 SNARK 预先算好并写进树里，算法和存款侧一样，是参考费率乘以写死的字节额度，这笔钱从提款人的 L2 余额里扣。所以拆分交易自带手续费，不需要任何人垫钱。如果之后费率上涨，给拆分交易加一个 P2A anchor 输出，任何人都可以用 CPFP 加速。
5. **数据可用性**：用户倾向把清单放在链上（2026-09-28）。放在链上有两种位置，比较如下：
   - **witness（推荐）**：
     - witness 同样在区块里，全节点都会存储，可用性和 OP_RETURN 一样。
     - 费用是 1 WU/字节，而 OP_RETURN 是 4 WU/字节。
     - 清单只出现一次：证明交易带一个很小的 OP_RETURN（放 R 和清单的平坦哈希，由 txid 承诺），vault 脚本对 witness 中的清单做一次 SHA256 核对即可。
     - 不进 txid 序列化，所以 b 第一层拆分时反射 vault 交易依然很便宜。
     - 容量：标准交易上限是 400k WU，按每笔提款 43 字节（金额 8 + 长度 1 + spk 34）算，大约能放近万笔。
   - **OP_RETURN**：
     - 费用是 witness 的 4 倍。
     - vault 脚本要重建 sha_outputs，就得在 witness 里再带一遍整份清单，等于付两次钱。
     - b 第一层每次反射 vault 交易，都要带上整份清单。
     - Core v30 默认的 relay 上限是 100KB，大约 2,300 笔。
     - 唯一的好处是被 txid 承诺，但 SNARK 并不需要从链上读回这份清单，因为清单是它自己生成的。
   - **应对 80 字节政策**（用户提议，可行）：把大数据切成不超过 80 字节的元素放进 witness，脚本里用 CAT 拼回去，再做一次 SHA256，和承诺值核对。父交易 T、祖父交易 Q 的反射数据也用同样的做法。
     - 元素个数：0xc0 在共识上限制栈和 altstack 合计 ≤ 1000 个元素，所以每个输入大约只能放 78KB；0xc2 的上限是 32,768 个，在标准交易 400k WU 以内不会成为约束。
     - 数据长度可变：脚本固定展开"最大块数"次 CAT，没用到的块用空元素补齐。CAT 空元素不改变结果，每个空元素只占 1 字节。
     - 如果没有 GSR（BIP347 下 CAT 的结果不能超过 520 字节），就改用哈希链 h = SHA256(h ‖ chunk)，但这时补齐用的空块需要跳过。
   - **前提**：GSR（0xc2）的 relay 政策目前还没有定义。现行 0xc0 的标准规则把每个 witness 元素限制在 80 字节以内，但我们的 covenant 本来就需要很大的 witness 元素（反射父交易和祖父交易），所以测试用的 signet 必须放开这个限制。这是整个设计的前提，不是清单独有的问题。
   - **已定（2026-09-28）：L2 的 DA 数据跟证明一起公布，放在 vault 自己的验证交易的 witness 里。**
     - DA 数据 = 提款清单 ‖ 状态变化。
     - **L2 账户模型和 DA 格式（已定，2026-09-28，`vault/src/da.rs`）**：
       - 账户 = 地址（32 字节，例如公钥，用来签 L2 交易；存款 OP_RETURN 里写的就是它）+ 余额 + nonce（这个账户发过几笔 L2 交易，用来防重放）。
       - 账户按编号 0、1、2……放在一棵 Merkle 树里；一个地址第一次出现时分配下一个编号。树根记为 l2_root，放在 vault 的应用状态里（§8.4），只有完成交易能改。design 里 S 已经用来指 vault 的状态信封，所以 L2 状态根不叫 S。
       - 编码全部用比特币的 CompactSize，只接受最短编码：
         - 提款清单：按共识格式序列化的 `Vec<TxOut>`（个数 + 各个输出）；
         - 新账户：个数 + 各自的 32 字节地址，按编号顺序（编号接着现有账户数往下排，不写出来）；
         - 变动账户：个数 + 每个账户的（编号与前一个的差，第一个与 0 的差；新余额；新 nonce），按编号严格递增。
       - 一个变动账户通常占 5～9 字节。存款在 L1 上本来就有，不另外公布。
     - **H 的定义与安全性**：
       - 定义：数据按顺序分成若干块，最后一环是 32 个零字节，每一环 = SHA256(块 ‖ 下一环)，H 是第一环。只有一块时，H = SHA256(DA 数据 ‖ 32 个零字节)。现在的实现就是这一种。
       - 安全论证：从 e = H 开始，每一步揭示 (块, 下一环)，其中下一环固定为 32 字节，要求 SHA256(块 ‖ 下一环) = e，然后令 e = 下一环；e 到达 32 个零字节时结束。
         - 只要没人找到 SHA256 的碰撞，每一步揭示的原像就是唯一的；而下一环是固定长度的后缀，决定了原像怎样切分，所以块和下一环都是唯一的。
         - 只要没人找到 32 个零字节的原像，链不会提前结束。
         - 归纳可知：揭示出来的块恰好就是 H 背后的那些块，顺序一致，一块不少。
     - 脚本对 DA 数据求哈希 H，H 是证明的公开输入。完成交易的 OP_RETURN 仍然是 `R ‖ H`（签名占位时需要它在交易里）。
     - 效果：不公布数据就完成不了验证，vault 会一直锁到超时，保证金罚没。所以状态前进和数据上链是同一件事。任何人都可以沿 vault 这条线读出每一批的 DA 数据，重放出完整的 L2 状态。
     - 容量：一笔标准交易（400k WU）大约能放 39 万字节。
     - 分块的扩展（以后需要时再做）：
       - 数据切成若干块，用哈希链承诺：最后一环是 32 个零字节，每一环 = SHA256(块 ‖ 下一环)，H 是第一环。
       - 验证期间增加"公布一块"的 vault 迁移：VERIFYING 状态记着下一个期待的哈希 e，一开始 e = H；每一步给出一块和它的下一环，检查通过后 e 换成下一环。
       - 完成交易要求 e 已经走到 32 个零字节。
       - 任何人都可以代为公布，因为每一步只有正确的那一块能通过。
     - 考虑过、没有采用的方案：
       - 证明语句里放一个 txid D，验证交易必须花 D 的输出（用户提议）。txid 不承诺 witness，数据只能放 OP_RETURN，费用是 witness 的 4 倍；要回到 witness 的价格，又得给每笔 DA 交易加一个自检程序 d，还要处理 D 的输出由谁来花的问题。放在 vault 自己的交易里，这些都不需要。
6. **ZK（待定，用户 2026-09-28 决定暂时搁置；验证器由其他人实现）**：怎么把证明放进交易、怎么验证，都还没定。
   - **占位验证器与接口（已定，2026-09-28，`vault/src/verifier.rs`）**：
     - **语句（证明的公开输入）**：`L ‖ acc′ ‖ l2_root ‖ l2_root′ ‖ B_min′ ‖ N′ ‖ W ‖ R ‖ H`，定长 212 字节。
       - L：vault 的 id；
       - acc′：完成之后的 acc，覆盖 vault 到锁定交易为止的全部历史；
       - l2_root、l2_root′：证明的起点和终点；
       - B_min′、N′：新参数；
       - W：付给 b 的金额；R：拆分树的根；H：DA 承诺。
       - 每个字段都由完成交易本身确定：W、R、H 在它的输出里，l2_root′ 和新参数在 caboose 里，L、acc′ 和 l2_root 经由它的父交易，由 vault 的 leaf 认证。
     - **l2_root 对 vault 是不透明的**，vault 不解释它，也不需要定义 L2 状态树。但必须保留这个值：它把相邻两次证明接起来，新证明的起点必须是上一次证明的终点，否则证明者可以从一个伪造的状态出发。
     - **占位：franking**。链下的 franker 先做电路里与 L2 内部无关的检查：
       - DA 数据是规范编码，并且与 H 一致；
       - R 和 W 恰好是由 DA 里的提款清单按规范布局构造出的拆分树（扇出和每笔拆分手续费是电路的配置）。
       - L2 的状态转移本身，也就是从 l2_root 按公布的状态差分到 l2_root′，视为成立。
       - 检查通过后，franker 用 BIP 340、SIGHASH_DEFAULT 对整笔完成交易签名，覆盖全部输入和输出。完成 leaf 用写死在 P 里的 franker 公钥做 CHECKSIGVERIFY。
     - **换成真正的验证器时**：链上把"检查 franker 的签名"换成"用上面的语句验证证明"；语句的各个字段在完成 leaf 的栈上都已经有了。多步验证、证明放在哪里，由做验证器的人决定。
     - **证明要读的历史，以及从哪里接着读**（2026-09-29，用户确认）：
       - 电路指证明所证明的那套规则；验证器只拿语句检查证明。
       - 电路要读的历史都由 acc′ 认证：acc′ 是 vault 每笔交易 txid 串成的哈希链，合并和存款交易又能从 vault 交易的输入 outpoint 一层层找到。所以电路把这些交易当作私有输入、逐笔算 txid 核对即可，链上不用加任何东西。假设节点都有完整的 L1、L2 状态。
       - 约定：L2 状态（由 l2_root 承诺）里记着"已经处理到的 acc"。新证明从旧状态里读出它，处理从它到 acc′ 之间的 vault 交易，新状态记下 acc′。这样相邻两次证明处理的历史首尾相接、不重叠，存款不会漏记也不会重记。
   - 以下是更早的说明，保留作记录：实现时的建议：先用 operator 签名作占位，也就是用普通 CHECKSIG 对整笔提款交易签名，0xc2 里有 CHECKSIG。接口按"验证语句 (acc′, R, 清单哈希, L1 链尖)"来留，以后替换成真正的验证器。原来的说明：目前是占位。如果验证器本身是一条多笔交易的 covenant 链，它产出的"证明已通过"输出被 vault 消费时必须经过认证（伪造问题同上）。参考 `~/bitvm-related/bitcoin-circle-stark`：仅用 OP_CAT 时要 72 笔交易、约 3.58M WU；原生 MUL/MOD 模型下脚本只有 12.5%。

     - 验证的第一笔交易花掉 vault，让它进入"验证中"状态。之后每一步验证都是 vault 自己的一次迁移，状态里记录验证进度。全部完成后执行提款，vault 回到正常状态。

     - 超时机制：N 个块内没有完成（比如证明是假的，根本算不下去），任何人都可以把 vault 恢复到正常状态。发起人要押保证金，超时就罚没。
   - 选项 B：验证放在一条独立的链上，vault 照常运转。
     - 证明绑定一个较早的 acc 检查点。vault 执行提款时，用中间各笔交易的 txid 重算哈希链，核对这个检查点确实是当前 acc 的祖先。
     - 用一个提款计数器，保证检查点之后没有发生过别的提款。
     - 验证链的最终输出，要用和 vault 相同的两代回溯来认证身份。
   - 两种选项都要处理"开始那一刻"的竞争：证明是针对某个 acc 生成的，生成要花几分钟到几小时，所以证明应该绑定检查点，而不是绑定最新的 acc。
   - **已定（2026-09-28）：选 A，验证期间锁住 vault。** 由此需要对 vault 做以下改动（草案）：
     - spec 的 envelope 不变，但 `app_root` 改为应用状态的承诺：`app_root = H(acc ‖ mode ‖ 模式相关的数据)`。mode 有两种：NORMAL；VERIFYING，此时带上语句哈希、验证进度（pc 和中间状态的哈希）、开始高度，以及发起人的 L2 奖励地址和保证金。
     - 进入 VERIFYING：花掉 vault，同时带上保证金输入。验证期间不允许并入，每一步验证都是 vault 的一次迁移，acc 照常累加父交易的 txid。
     - 验证完成：执行提款（§7），退还保证金，mode 回到 NORMAL。
     - 超时：单独加一条 tapscript leaf。
       - 按 spec 的 ENV-2，这条 leaf 同样要执行完整的 UTXO line 规则（身份、后继、caboose、acc），只是把 mode 改回 NORMAL、罚没保证金，而不是一个逃生出口。保证金的去向待定。
       - 用 CLTV（绝对高度），不用 CSV。CSV 是按被花的那个 UTXO 计时的，而验证每走一步都会产生新的 vault UTXO，计时会被重置，拖延的人可以每一步都卡在超时之前。
       - 具体做法：进入 VERIFYING 的交易把 nLockTime 设为当前高度 h，脚本从 sighash 读出 h，记进状态；超时 leaf 要求 nLockTime ≥ h + N（OP_CHECKLOCKTIMEVERIFY）。这两笔交易的 nLockTime 不是 0，这又是一处对 spec 的偏离。
     - 开始时刻的竞争（已定，用户方案：先锁定，再生成证明）：
       - 先发一笔交易，把 vault 锁进 VERIFYING。抢的只是这一笔便宜的交易；如果被别人的并入交易抢先，就基于新的 vault 重发，不会有任何证明白做。
       - 锁住以后 acc 就冻结了，再针对这个冻结的 acc 生成证明，然后上链验证。用户估计生成证明不会花太久。
       - 因此不再需要检查点、祖先核对和提款计数器。
       - 锁定交易发出时证明还不存在，所以它不承诺语句；语句在第一步验证时写进状态。
       - 超时 N 要足够覆盖"生成证明 + 链上验证"两段时间。
       - 新的风险是有人锁住 vault 却不提交证明，把 vault 卡住 N 个块。靠保证金罚没来威慑。
       - 已定（2026-09-28）：任何人只要押保证金就能锁定。保证金被罚没时进入 vault，由 L2 做最终裁决和分配（SNARK 沿 acc 可以看到锁定交易和它最终是怎样结束的）。
       - 已定（2026-09-28）：保证金在 L1 上退还。用户的理由是，如果走 L2 退，资金周转太慢。
         - 锁定时：保证金并入 vault 的余额。VERIFYING 状态里记下保证金金额、退款地址（锁定者的 L1 spk）和锁定者的 L2 奖励地址。
         - 验证成功（最后一步加上提款）：vault 脚本强制产生一个输出，把保证金付回退款地址，vault 余额相应减少。
         - 超时：不产生退款输出，保证金留在 vault 里，由 L2 裁决。
         - 做验证工作的奖励仍在 L2 上发，记到锁定者的 L2 地址。
       - 已定（2026-09-28）：最低保证金 B_min 放在应用状态里，由证明更新。
         - B_min 的初始值写进创世状态。之后只有验证成功的那一步可以按证明给出的新值改写它，其他迁移都原样保留。
         - 超时 N 默认和 B_min 同样处理，即放在应用状态里、由证明更新；用户有不同意见再改。
       - 用户说明（2026-09-28）：之前提到"聚合者之间可能互相报复、互相伤害"，只是为了说明保证金应该在 L1 上退款，并不需要额外的防护机制。我提过的"罚没赔偿 / 冷却期 M / 抢交易无害"三层方案不采用，保持简单：只用保证金 + 超时 + L1 退款，罚没部分由 L2 裁决。
   - **实现（P4b，2026-09-28，`vault/src/leaf.rs`、`tx.rs`）**：
     - 应用状态：`acc(32) ‖ mode(1) ‖ l2_root(32) ‖ B_min(LE64) ‖ N(LE32)`，共 77 字节。VERIFYING 时后面再接 `h(LE32) ‖ 保证金(LE64) ‖ 锁定者 L2 地址(32) ‖ H(退款 spk)(32)`，共 153 字节。l2_root 是后来加的（见 §7 第 5 条），和参数一样只有完成交易能改。
     - vault 的树有 8 个 leaf，每种交易一个。所有种类的输入都是 `[vault, (存款…), fee]`，输出都以 `[vault, change, …]` 开头、以 caboose 结尾：

       | 种类 | mode | 中间的输出 | vault 金额 | nLockTime |
       |---|---|---|---|---|
       | 普通迁移 | NORMAL → NORMAL | 无 | 不变 | 0 |
       | 并入 j = 1～4 | NORMAL → NORMAL | 聚合者 OP_RETURN | + Σ存款 | 0 |
       | 锁定 | NORMAL → VERIFYING | 无 | + 保证金（≥ B_min） | h |
       | 完成 | VERIFYING → NORMAL | b、OP_RETURN(R ‖ H(清单))、退款 | − W − 保证金 | 0 |
       | 超时 | VERIFYING → NORMAL | 无 | 不变（保证金留在 vault） | ≥ h + N（CLTV） |

     - 锁定：h 就是锁定交易自己的 nLockTime，脚本要求它是区块高度（< 500,000,000）。共识保证 h 不超过当时的链高度；锁定者把 h 设小，只会让自己更早被超时。
     - 完成：
       - 清单作为 witness 元素传入，脚本核对 SHA256(清单) 等于 OP_RETURN 里的哈希（DA）。
       - 证明的占位：franker 在链下检查语句之后，用 CHECKSIG（SIGHASH_DEFAULT）对整笔交易签名，公钥写死在 P 里（见 §7 第 6 条）。
       - 新的 l2_root 和新参数 (B_min′, N′) 作为 hint 传入，由签名（以后由证明）认可。
       - 退款输出的 spk 不能是 P。否则完成交易会多出一个 P 输出，下一次迁移解析这笔交易时会失败，vault 就被永久冻结了。锁定者如果把退款地址设成 P，这次锁定只能等超时。
     - 验证期间只能执行"完成"和"超时"，并入、普通迁移和再次锁定都会被拒绝。
     - 占位只需要一步，所以还没有"验证步骤"这种迁移。等真正的验证器确定之后，再加上多步验证和它的进度字段。
     - 大小（加入 l2_root 和 DA 数据之后）：锁定 1,093 vB；完成 1,396 vB（DA 数据约 100 字节）；超时 1,098 vB；普通迁移 1,076 vB。leaf 大小 2.3～2.7 KB。
     - 模拟器新增了区块高度，并按共识检查 nLockTime 是否已经生效（IsFinalTx）。"h + N 之前无法超时"这条性质因此能完整测到：nLockTime 小于 h + N 时 CLTV 失败；等于或大于 h + N 时，交易在高度 h + N 之前还没有生效。
   - 原先的倾向：A 加检查点；检查点这部分已被"先锁定，再生成证明"取代。GSR 下验证可能只需要两三笔交易（按 op-mulmod 的估算，约 0.7M WU，这是推算），一个块就能完成，vault 被锁的时间很短。只用 OP_CAT 时是 72 笔的链，超过 mempool 默认 25 笔未确认祖先的上限，至少要跨 3 个块。
5. 逃生通道：L2 停摆时 vault 需要逃生路径。program a 不做退款，所有失败情形都依赖这条路径。注意 spec 禁止终止（LIN-3）。
   - 用户问（2026-09-28）：L2 如果是去中心化的，是不是就不会停摆？
   - 分析：去中心化加上 permissionless 证明（任何人押保证金就能锁定并提交证明，这一点已经有了），可以消除"operator 消失"这种停摆。但停摆还有另外三个来源：
     1. 数据不可得：没人能重建 L2 状态，也就没人能出证明。所以 L2 的数据放在哪里（DA）是关键：L2 状态的变化如果能从 L1（或者足够可靠的 DA）上重建，任何人都能接着证明下去。
     2. 审查：用户的 L2 交易被排除在外。解决办法是强制包含：用户可以通过 L1 交易把"强制提款请求"放进 acc，下一个证明就必须处理它。存款现在已经有这个性质了。
     3. 电路或验证器有 bug，导致谁都证不出来：去中心化解决不了。只能靠升级机制或逃生通道，而 spec 目前两者都不支持。
   - 结论（提议）：满足 1 和 2，就可以不做逃生通道；bug 的风险单独考虑。下一个问题：L2 的数据放在哪里？
   - 用户意见（2026-09-28）：
     - DA 是个老问题，用户打算今晚拿出来讨论。现在的 DA 层基本都停止运营了，所以大概率还是要放在比特币上，哪怕只是临时的 DA 也需要。
     - 一个思路是和证明放在一起：证明的过程中，至少要把"状态变化"公布出来。这可以沿用提款清单的做法：把状态变化放进验证交易的 witness，证明的公开输入里带上它的哈希，由脚本核对。这样交易一上链，数据就被公布了。
     - 审查问题处理不了，只能依靠去中心化，不做针对 L2 交易的强制包含机制。
     - 由此，逃生通道倾向于不做，具体等 DA 讨论之后再定。
